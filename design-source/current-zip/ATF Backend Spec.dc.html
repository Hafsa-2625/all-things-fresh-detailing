All Things Fresh — backend build spec v1 · 28 August 2026

Backend, CMS and page expansion under an absolute design freeze

This document is the implementation contract for the All Things Fresh website. The approved public design is the visual source of truth and does not change. Everything below describes what may be built behind it, what the admin may edit, and how each stage is proven not to have altered a single pixel of the public pages.

1. Scope

In scope Out of scope
Structured content fields bound to existing components. CRM: leads, customers, vehicles, quotes, jobs, appointments, invoices, payments. Notification routing. SEO metadata, structured data, redirects. Four public page templates covering 60+ new URLs. A separate authenticated admin interface. Visual-regression test suite. Any change to public layout, typography, colour, spacing, imagery, animation or section order. Any redesign or modernisation. Any visual page builder. Any new public design pattern. Dependency upgrades that alter rendering. Global theme controls.

4. What the admin cannot reach

These controls are not disabled in the interface. They are never rendered, and no API route accepts them. Changing any of them is a code change gated behind a passing visual-regression run.

Font family · font size · font weight · line height · letter spacing · text colour · background colour · gradient · border · corner radius · shadow · padding · margin · gap · container width · grid columns · breakpoints · section order · section structure · element position · z-index · animation timing · animation easing · hover and focus styling · component styling · custom CSS · custom JavaScript · arbitrary page-builder blocks · section drag-and-drop · global theme replacement.

Two content-side guards follow from the same principle. Text fields carry character limits derived from the space the approved component gives them, so no entry can wrap a heading onto an extra line. Image uploads are re-encoded to the slot's exact pixel dimensions, so no upload can change the height of a section.

The thirty-six location pages are the duplicate-content risk. Each one requires two genuinely local paragraphs, its own neighbourhood list, its own drive time, and at least one review from a customer in or near that city. The admin blocks publishing a location page whose body text is more than 70% similar to any other location page, and the SEO view surfaces those overlaps before they go live.

Deterministic capture rules

The homepage has four running animations, so a naive screenshot test fails at random. Each of them is pinned to a fixed frame before capture, not disabled:

Moving element Pinned state for capture
Dirty / clean car masksThree captures per viewport, at animation-delay 0s, 4.25s and 8.4s
Floating logo and its shadowPaused at 0s
Review carouselTimer stubbed, index forced to 0
Before/after sliderHandle set to 55%, the default
Social carouselscrollLeft 0, Instagram tab active
Google Maps iframeMasked. It is genuinely dynamic third-party content. Its container box is asserted separately by bounding-rect check, not by pixels.
YouTube posterStubbed to a fixture image so thumbnail changes do not fail the run

Web fonts are loaded from a local fixture rather than the Google Fonts CDN during tests, and every run waits on document.fonts.ready plus all image decodes before capturing. Nothing else is masked. Masking a layout area to make a diff pass is treated as a failed run.

Gate for every stage

  1. Render each existing public page at every viewport in the matrix.
  2. Diff against the approved baseline at a zero-tolerance threshold, with a 1px anti-aliasing allowance only.
  3. Assert bounding rectangles for the hero panel, nav pill, each card grid, the booking form and the footer, so a diff that passes visually still fails if geometry moved.
  4. Assert computed styles for the ten type tokens and nine colour roles in section 2.
  5. Assert a cumulative layout shift of 0 on every page.
  6. Investigate every unexplained pixel. No stage is approved while one remains.

Public pages must load no admin bundle. That is asserted directly: the test fails if any request from a public route resolves to an admin chunk, or if any admin stylesheet rule is present in the page's style sheets.

7. Open items needing your approval

The freeze says to stop and flag rather than invent. These are the flags.

1. Typography discrepancy: Outfit versus Arial
The freeze instruction names Outfit as the approved typeface. The approved build sets font-family: Arial, Helvetica, sans-serif on the body and loads only Alex Brush and Great Vibes. Since the built output is the visual source of truth, the templates match the build and use the Arial stack. Confirm which is correct. Switching to Outfit is a deliberate visual change to every page and needs its own baseline.
2. Subpage hero has no approved baseline
Only the homepage hero exists today. The templates reuse its radial-gradient panel, its 20px radius and the nav pill exactly, but the panel grows with content instead of holding a fixed aspect ratio, the car pair is omitted, and the page title uses the approved section-heading token rather than the Alex Brush wordmark. Those are the three decisions to confirm.
3. Long-form prose scale
The approved build has no article body copy. The resource template derives one: 16px / 1.7 body from the existing 15–18px lede, and 28px / -0.05em subheads sitting between the existing 24px card heading and the 39px section heading. No new colours or faces. Confirm the two derived sizes.
4. Nav active state on subpages
The approved nav marks Home with the dark #2c3033 pill. On a service or location page the active item should arguably move to Services. The templates leave Home active so nothing differs from the baseline. Confirm whether the pill should follow the current route.
5. Nav capacity at 36 location pages
The nav pill holds five items plus the phone number and Contact button. Thirty-six location pages cannot be surfaced there. The templates reach them through the footer city list and a /service-area index page. Adding a dropdown to the nav would be a new public pattern, so it is not built. Confirm the footer route is acceptable.
6. Missing baseline screenshots
The matrix in section 6 includes one entry per supplied approval screenshot. Those screenshots have not been supplied to this project. Send them and the matrix can be completed; until then only the three standard viewports are covered.
